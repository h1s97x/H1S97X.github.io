验证码是爬虫路上最经典的一道墙，也是一场没有终点的猫鼠游戏。这个系列一共四篇，从类型到落地：本篇讲分类和思路，后面三篇分别讲文字验证码识别、滑块缺口的定位与轨迹、以及点选/行为验证与打码平台。

先说明立场：**只用于自己账号的自动化、安全测试和学习，不要拿去批量薅羊毛或撞库**。验证码是别人的防护设计，绕过它属于对抗行为，越界就变成法律问题。

## 一、验证码到底是什么

CAPTCHA 全称 Completely Automated Public Turing test to tell Computers and Humans Apart。名字很长，本质只有一件事：**出一道机器难以稳定通过的题，让机器在成本上不划算**。

注意它不追求"机器绝对做不到"——人脸识别都被攻克了，图片题自然也能。它追求的是**让单位成本高于收益**：你过一道滑块要 3 秒和 2 分钱，别人就达到目的了。

所以破解验证码的核心不是"变魔术"，而是回答一个经济学问题：**我的方案成本，能不能压到低于目标价值**。这一点决定了后面所有技术路线的取舍。

## 二、按识别方式重新分类

网上常见的分类是按外观分：文字、滑块、点选、语音。这个分法不方便定位技术方案，我更喜欢按**"这道题到底在考什么"**来分：

| 类型 | 考的能力 | 拿到答案靠什么 | 典型产品 |
| ---- | -------- | -------------- | -------- |
| 文字型 | 图像里的字符 | OCR / 深度学习 | 老式 ASP 站、教务系统 |
| 图像匹配型 | 缺口/旋转角度 | 边缘检测、模板匹配 | 极验滑块、网易易盾 |
| 目标定位型 | 图中的物体在哪 | 目标检测（YOLO） | 腾讯防水墙、12306 |
| 行为型 | 你像不像人 | 轨迹生成 + 环境伪装 | reCAPTCHA v3、阿里无感 |
| 协议型 | 令牌怎么算出来的 | 逆向 JS / 协议分析 | 几乎所有滑块 |
| 语音型 | 音频里的数字 | ASR | reCAPTCHA 无障碍入口 |

这张表的价值在于：**同一道题往往同时属于两三类**。极验滑块既是"图像匹配型"（要算缺口位置），也是"行为型"（要看轨迹），更是"协议型"（validate 参数要算对）。三关全过才算通过——这也是滑块比文字验证码难的根本原因。

## 三、四条技术路线

不管哪种验证码，绕过去的路子其实只有四条，按成本从低到高：

### 1. 识别（Recognition）

把图上的信息读出来：OCR 认字符、边缘检测找缺口、YOLO 找物体。

这条路线的前提是**你能拿到原始图片**。如果图片本身就是加密的、拼过的、带着动态干扰的，那得先走路线 4。

### 2. 模拟（Simulation）

把人的操作伪造出来：鼠标轨迹、点击节奏、拖动速度、甚至键盘的犹豫停顿。

现在的验证码几乎都在服务端做行为分析，**"滑到正确位置"只是及格线**，轨迹不自然人照样不通过。这一块是新手最容易翻车的环节，第三篇会细讲。

### 3. 逆收（Protocol Reverse）

不去模拟人，直接算对它要的参数：极验的 `w`、reCAPTCHA 的 token、自研站点的签名。

这是**最彻底也最贵**的路线：要脱混淆、要跟算法、要跟版本更新。但一旦打通，稳定性和速度远胜模拟方案。

### 4. 外包（Outsource）

把图丢给打码平台或人工。不是技术投降，而是**成本核算之后的理性选择**：一张图 0.5 分钱、10 秒返回，比你自己维护一套识别模型便宜得多。

## 四、一个可落地的决策流程

真正做项目时，我按这个顺序试：

```
拿到目标站的验证码
│
├─ 1. 抓包看返回的是什么
│   ├─ 有明文答案？→ 直接抄（真的存在，别笑）
│   ├─ 图片明文可下载？→ 走识别
│   └─ 图片加密/拼接？→ 看 JS，走逆收
│
├─ 2. 先试最简单的识别
│   ├─ 文字 → ddddocr，一行代码
│   └─ 滑块 → ddddocr 检测 或 OpenCV 模板匹配
│
├─ 3. 识别能出结果，但提交不通过？
│   ├─ 大概率是轨迹/行为被判 → 上轨迹模拟
│   └─ 还有可能是设备指纹 → 上真实浏览器 + Stealth
│
├─ 4. 全都不行
│   └─ 打码平台兜底，成本可控就收工
│
└─ 5. 量特别大
    └─ 才值得考虑逆协议 / 自训模型
```

关键在于**按成本递增去试**。很多教程一上来就让你训模型、脱混淆，纯属浪费——80% 的场景用 ddddocr + 打码平台兜底就够了。

## 五、几个容易踩的认知坑

**坑一：以为识别率是唯一指标。**
识别准确率 95% 但提交 10 次才过一次，不如识别率 80% 但轨迹自然、一次通过。

**坑二：只在无头浏览器里调试。**
无头模式的指纹特征（`navigator.webdriver`、缺失的插件列表、异常的 WebGL 参数）早就被识别了。调试可以无头，实战必须真浏览器或伪装到位。

**坑三：忽视请求频率。**
验证码只是第一道关，后面还有 IP 频率限制、账号行为风控。把你自己的行为搞成"正常人"，比把验证码过掉更重要。

**坑四：以为破解了就一劳永逸。**
验证码服务商是按季度迭代的。今天通了的方案，下周可能就废了。**给方案留降级路径**（识别 → 打码平台）比追求单个方案完美更实际。

## 六、本系列安排

- 第二篇：**文字验证码** —— ddddocr、Tesseract、OpenCV 预处理，以及"识别不准怎么办"
- 第三篇：**滑块验证码** —— 缺口定位（模板匹配 / 边缘检测）、轨迹生成（贝塞尔、过冲、回退）、ghost-cursor
- 第四篇：**点选与行为验证** —— YOLO 目标检测、reCAPTCHA/hCaptcha 的 token 获取、打码平台接入

写完这四篇，你应该能独立判断一个新站的验证码该走哪条路。
